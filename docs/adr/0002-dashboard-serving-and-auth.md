# Serve the dashboard from the same binary, authenticated with the existing API key

xmail serves its account-management web dashboard as a handful of `go:embed`-ed static assets (HTML/CSS/JS) mounted outside the `X-API-Key` middleware on the same `http.Server`, port, and `ServeMux` as the REST API and MCP. The dashboard's JavaScript collects the API key on a login screen, keeps it in `sessionStorage`, and attaches it as `X-API-Key` to every API call it makes. A page's own HTML/CSS/JS requests cannot carry a header, and those assets contain no secrets, so they are served without auth; every endpoint behind them stays protected exactly as before (`internal/api`, `isAPIPath`). Rejected for now: a cookie-session variant (a login endpoint that exchanges the key for an `HttpOnly` session cookie), which would hide the key from JavaScript but needs server-side session state and a new endpoint — out of proportion for a single-static-key MVP, and a new place for auth bugs to hide. Also rejected: a separate frontend origin (React/Vite with a CORS middleware), which would add a Node build step to a project whose whole point is one static binary and no toolchain beyond Go. The trade-off accepted is that the key lives in browser storage, mitigated by a same-origin-only CSP (`default-src 'self'`, no inline script/style, no CDN) and by never rendering server data with `innerHTML`. Multi-key auth (`PLAN.md` Fase 9) would let each dashboard user hold their own key later without changing this decision.

Status: accepted. Implemented — `internal/dashboard` (`Handler()` + embedded `assets/`), `internal/api.Server.dashboard` with the `isAPIPath` routing predicate, wired by `internal/app.Run`; covered by `internal/api/dashboard_test.go` (assets are public, the API is not) and `internal/dashboard/dashboard_test.go` (asset integrity, CSP compliance). See `PRD.MD` §6.7 and `PLAN-DASHBOARD.md`.
